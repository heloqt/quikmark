# PDF 导出技术验证

## 1. 验证结论

日期：2026-10-22

wxPdfDocument 1.4.0 可以在当前项目工具链中工作：

- wxWidgets 3.3.4，MinGW-w64 GCC 16.2，静态链接。
- TrueType 字体 `simhei.ttf` 和 TTC 字体 `msyh.ttc` 均能注册和嵌入。
- 中文 PDF 文本可由 pypdf 正确提取，说明文字可选择、可搜索。
- `wxPdfDC` 可以通过 wxWidgets 的 `wxDC` 绘制接口直接输出中文 PDF。
- 字体子集化生效：约 9.3 MiB 的黑体只让单页测试 PDF 增加约 28 KiB 字体数据。

因此 wxPdfDocument **技术可行**。主要工作量仍是将当前屏幕渲染器改造成独立的分页渲染器。

## 2. PoC 产物

| 产物 | 大小 |
|---|---:|
| `libwxpdfdoc.a` | 9,616,324 字节（9.17 MiB） |
| 相同配置的 wx GUI 空程序 | 13,935,194 字节（13.29 MiB） |
| wxPdfDocument 中文样例程序 | 17,593,589 字节（16.78 MiB） |
| wxPdfDC 中文样例程序 | 17,781,066 字节（16.96 MiB） |
| 黑体单页中文 PDF | 28,594 字节 |
| 微软雅黑 TTC 单页中文 PDF | 54,294 字节 |
| wxPdfDC 单页中文 PDF | 22,393 字节 |

静态库归档大小不等于最终程序增量。以相同 wxWidgets GUI 空程序为基线：

- wxPdfDocument API 增量约 **3.49 MiB**。
- wxPdfDC API 增量约 **3.67 MiB**。

当前安装器为 `3.89 MiB`。按相同压缩率粗估，合入后安装器可能增加约 `0.8–1.5 MiB`，仍应低于 `10 MiB`，但正式合入后必须重新测量 NSIS 安装器。

PoC 排除了当前产品不需要的条形码和 WOFF/WOFF2 可选模块。使用 TTF/TTC 字体不受影响。

许可证为 wxWindows Library Licence，包含允许二进制分发的例外条款；发布时必须附带相应许可证文本。

## 4. 与 Windows 打印为 PDF 比较

| 维度 | wxPdfDocument | Windows 打印为 PDF |
|---|---|---|
| 安装包 | 预计增加约 0.8–1.5 MiB | 基本不增加 |
| 输出入口 | 应用内直接选择文件名并导出 | 进入系统打印对话框，再选择保存位置 |
| 系统依赖 | 无虚拟打印机依赖 | 需要 `Microsoft Print to PDF` 和打印后台服务 |
| 文字质量 | 库直接生成矢量文字和图形 | 取决于 Windows 打印驱动 |
| 字体控制 | 可指定字体、嵌入和子集化 | 由系统打印驱动管理 |
| 书签、链接、元数据 | 可直接控制 | 受打印驱动和打印框架限制 |
| 页面控制 | 可完全控制 A4/页边距/分页 | 通过 wxPrintout 控制，系统对话框参与 |
| 自动化测试 | 可直接生成文件并检查内容 | 需要处理打印对话框和系统打印机 |
| 可移植性 | 有基础；当前仍只验收 Windows | 绑定 Windows 打印体系 |
| 开发工作量 | 2–4 周完成当前内容范围 | 约 1.5–2.5 周 |

两种方案都必须完成同一项核心改造：把当前视口渲染改成独立的 A4 分页渲染。wxPdfDocument 主要额外帮助是省去 PDF 文件格式、字体子集和 PDF 对象写入工作。

## 5. 建议

如果 PDF 导出要求：

- 应用内一键直接导出；
- 固定版式和字体；
- 可搜索、可选择的中文文本；
- 后续要支持书签、超链接、PDF 元数据或 PDF/A；

则推荐采用 **wxPdfDocument + wxPdfDC**。验证表明它的包体增量仍在当前 `<10 MiB` 预算内。

如果只需要偶尔“另存为 PDF”，并且可以接受系统打印对话框和虚拟打印机依赖，则 Windows 打印为 PDF 更轻。

当前产品的长期方向更适合 wxPdfDocument。正式开发应先抽出分页渲染器，再接入 `wxPdfDC`，避免把 PDF 后端逻辑侵入 `DocumentView`。
