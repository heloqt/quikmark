# 因为不想再等 Electron：我用三个晚上写了一个原生 Markdown 阅读器

这个故事的开头，并不是我想做一个软件。

开始大量使用 AI 编程之后，我和同事的交流方式发生了变化。需求、设计方案、问题分析和代码说明，越来越多地以 Markdown 形式产生。它们比聊天记录完整，比口头描述更容易回溯，也不需要像 Word 那样反复调整样式。真正麻烦的是“交付”环节：发 Word 不方便协作，转 PDF 又很难继续编辑，最后往往还是保留一份 `.md` 文档。

文档有了，阅读体验却一直不太顺手。

用 VS Code 看 Markdown 当然可行，但它首先是一个编辑器。为了同时看到源码和预览，页面通常要分成两栏；如果本来就在双屏或宽屏上工作，再被编辑器、资源管理器和预览区切走一大块空间，真正留给正文的宽度就不多了。更尴尬的是，我只是想“看懂一份 AI 生成的文档”，并不需要编辑、调试、插件和整个 IDE。

于是我开始找现成的 Markdown 阅读器。

Typora 的口碑很好，所见即所得，编辑体验也成熟，但它是收费软件。后来我找到 Mark Text，作为免费替代品，功能不少，界面也不错。问题出在大文档上：在我的机器上打开一份约 150 KB 的 Markdown，经常要等 10 秒以上；两个已经打开的 Tab 之间切换，也要四五秒。对日常只读几百 KB 技术文档的人来说，这个等待会不断打断思路。

那一刻我意识到，自己想要的其实不是另一个编辑器，而是一个**只负责把 Markdown 快速、安静地显示出来**的工具。

所以这次我没有急着比较框架，而是先给速度定了一条很朴素的线：打开文档不能以秒计，切换 Tab 要接近无感。至于最后有没有做到，不如先把结果放在这里。

## 先看结果：从等待几秒到毫秒级响应

这里的冷启动统一计时到首个可读视口完成绘制。150 KB 文档虽然小到体感上几乎像一次性全部打开，但仍和 10 MB 使用同一个终点。先只挑一台普通办公机看结果：在 Intel i5-14500 上，150 KB 文档的冷启动 P50 是 **156.7 ms**，Tab 切换是 **4.7 ms**；10 MB 文档分别是 **173.8 ms** 和 **19.8 ms**。

这里只放冷启动和 Tab 切换的中位数，完整的 P50/P95、运行中打开、滚动以及另一台 AMD 机器的数据放在后面。

Mark Text 的“10 秒、四五秒”是人工使用感受，不能和这里的应用内计时直接横比；但“等待几秒”和“毫秒级响应”之间的体验差异是真实存在的。

不过，这些数字是结果，不是起点。它们真正说明的事情只有一件：一个目标足够窄的阅读器，有机会把等待压缩到几乎不被注意。至于为什么能跑到这里，还要从我对“只读”这两个字的取舍说起。

## 先把需求缩小：只读就够了

AI 生成的文档通常在 VS Code 里修改，阅读器只需要负责查看。这个前提一旦明确，需求就简单了很多：

- 双击文件后尽快看到正文。
- 一个窗口内用 Tab 管理多份文档。
- 支持常见 Markdown、表格、图片和基础流程图。
- 启动、打开、切换和滚动都不能有明显等待。
- 不引入编辑器、插件市场、云同步和复杂工作区。
- 尽量小，能在 Windows 上直接安装和运行。

最后一条尤其重要。如果为了渲染 Markdown 再打包一个 Chromium，那么应用还没开始显示文档，就要先承担浏览器内核的启动和内存成本。这与“快速打开一份参考文档”的初衷正好相反。

## 为什么最后没有选择 WebView

一开始我比较了几条常见路线。

| 方案 | 优点 | 主要问题 |
|---|---|---|
| Qt + WebEngine | Web 渲染成熟，Markdown 前端生态丰富 | 包体和内存开销大，本质上仍然带着浏览器内核 |
| Qt WebView | 原生外壳，可复用部分 Web 内容 | 仍依赖平台 WebView 和 HTML 渲染链路，行为与部署环境相关 |
| wxWidgets + wxWebView | GUI 是原生的，界面开发相对直接 | Windows 上通常会落到 WebView2，真正显示仍由 Web 引擎完成 |
| wxWidgets + md4c | 原生绘制、依赖少、性能路径可控 | Markdown 排版、表格、选择、绘制都需要自己实现 |

前三种方案都能更快做出“能显示 Markdown”的原型，但它们没有解决我最在意的问题：启动后还要拉起 Web 渲染层，复杂页面仍要经过 HTML、CSS 和浏览器布局。包体小不等于首屏快，而首屏快也不只是换一个 GUI 框架就能自动得到。

最终我选择了更“笨”、但更贴近目标的组合：

> C++17 + wxWidgets 3.3 + md4c + 自研 Markdown 布局与绘制

wxWidgets 负责原生窗口、菜单、剪贴板、文件对话框和暗色主题；md4c 负责把 Markdown 解析成轻量事件流；文档模型、块级布局、表格绘制、搜索、选择和流程图则由项目自己实现。

流程图最初考虑过 Graphviz/libgvc 和 Cairo。它们的能力更完整，但会增加构建依赖和发布包体，libgvc 还有全局状态和线程安全方面的顾虑。最终我只实现了常用的 Mermaid flowchart 子集，用受限解析器和自研分层 DAG 布局完成绘制。遇到不支持的语法，不猜测、不隐藏，直接降级显示原始代码。

这也是整个项目最重要的取舍：**不追求一次支持所有 Markdown，而是先把最常见的阅读路径做好。**

## 第一个晚上：先让它把文件打开

第一晚的目标很明确：不做“大而全”，先跑通最小阅读闭环。

工程使用 CMake 和 MinGW-w64，界面用 wxWidgets 3.3，解析器接入 md4c。窗口里没有编辑按钮，也没有源码与预览切换，只有文档区和 Tab。打开、拖入和文件关联最终都进入同一条打开请求路径；同一个文件不会重复创建 Tab；应用已经运行时再次双击文件，新进程会把路径转发给已有窗口，然后自己退出。

第一版很快遇到了一个架构问题：如果解析、布局和绘制都放在 UI 线程，哪怕文档只有几百 KB，打开时窗口也会短暂无响应。于是文件读取和 Markdown 解析被移到后台线程，UI 线程只接收已经完成的事件并负责布局和绘制。取消、关闭 Tab、重新加载和解析代次也必须一起处理，否则旧文档的解析结果可能覆盖新文档。

到第一晚结束时，它已经可以打开 UTF-8/BOM Markdown，完成基础分段和样式显示，在多 Tab 间切换，并保持单实例运行。它还称不上成熟，但已经不再是“只能打开一个空窗口”的骨架。

## 第二个晚上：从“能看”变成“愿意用”

第二晚主要补齐真实文档需要的内容。

表格不能简单按照固定列宽铺开。我加入了内容感知列宽、表头样式、斑马纹和超宽表格内部横向滚动。图片支持本地路径、相对路径和 HTTP/HTTPS 异步下载。链接交给系统默认浏览器打开，视觉上保持可点击提示。

流程图没有塞进一个完整 Mermaid 引擎，而是支持流程图里最常见的部分：方向、矩形、圆角、菱形、圆形节点、连线、边标签和单层子图。布局在后台完成，首屏先显示占位，完成后替换。无法识别时保留源码。

阅读器还需要一些“看起来不起眼，但少一个就不顺手”的能力：

- 鼠标跨块选择文字并复制为纯文本。
- `Ctrl+F` 临时查找、高亮和上下文跳转。
- 可收回、可常驻的目录侧栏。
- 跟随系统、浅色和暗色主题。
- `Ctrl+鼠标滚轮` 调整字号。
- 文件变化提示、手动重载和最近打开。
- 窗口位置、Tab 顺序、阅读位置和目录状态恢复。

这一晚之后，它才开始像一个真正的阅读器，而不是一次技术验证。

## 第三个晚上：真正难的是首屏时间

功能补齐后，打开大文件仍然会有可感知的停顿。起初我以为是文件读取慢，拆开计时后才发现，读取 10 MB 文件通常只需要几毫秒，真正耗时的是 md4c 全文解析、块模型后处理和首次布局。

最初 10 MB 文档的冷启动约在 `600–630 ms`。第一版优化集中在布局初始化，收益只有几毫秒；因为只要首屏仍在等待完整文档解析和所有块的高度估算，优化局部循环并不能改变主路径。

真正的转折是把工作拆成“前台首屏”和“后台完整解析”：

1. 文件仍在后台读取并校验 UTF-8。
2. 在前 32 KB 内寻找安全的顶层 Markdown 边界，不会从代码块中间生硬切开。
3. 只解析这段安全前缀，先布局并绘制第一屏。
4. 同一后台任务继续解析全文。
5. 全文完成后再替换临时模型，同时保持用户当前阅读位置。

这一步让首屏不再等待全文。10 MB 文档的首屏布局初始化从约 `43.8 ms` 降到 `0.141 ms`，冷启动从约 `600 ms` 降到 `325 ms`。

接着处理另一类极端情况：文档虽然不大，但包含一个超长段落或一个超大表格。这样的单个块可能直到文件末尾才闭合，之前的块级虚拟化对它没有意义。解决方案是在模型后处理阶段继续拆分：

- 单个文本块超过 12 KiB 时，在换行、空格或合法 UTF-8 边界处切成连续显示块。
- 单个表格超过 64 个数据行时，拆成共享列宽提示的连续表格块。
- 拆分只影响布局，不改变复制内容、搜索顺序和源文本顺序。

同时，解析任务在完成或取消后被及时回收，避免长时间打开多份文档时线程句柄不断增加。第三晚的最后，我补上性能脚本、单元测试、安装器和静态发布包，让它从“自己电脑上的 Demo”变成可以交给别人运行的软件。

## 完整性能数据与测试环境

AMD Ryzen 7 8845HS 笔记本使用 20 个 150 KB 样本和 5 个 10 MB 样本；Intel i5-14500 台式机使用当前优化版测试，150 KB 的冷启动、运行中打开和 Tab 切换分别使用 20、20、40 个样本，10 MB 对应使用 5、5、20、30 个样本。

| 场景 | AMD 8845HS P50 | AMD 8845HS P95 | Intel i5-14500 P50 | Intel i5-14500 P95 |
|---|---:|---:|---:|---:|
| 150 KB 冷启动首屏 | 284.701 ms | 314.635 ms | 156.676 ms | 191.805 ms |
| 150 KB 运行中打开 | 20.746 ms | 25.393 ms | 15.438 ms | 19.875 ms |
| 150 KB Tab 切换 | 7.228 ms | 10.326 ms | 4.677 ms | 6.497 ms |
| 10 MB 冷启动首屏 | 325.682 ms | 328.849 ms | 173.757 ms | 180.478 ms |
| 10 MB 运行中打开 | 17.888 ms | 30.918 ms | 20.228 ms | 21.123 ms |
| 10 MB Tab 切换 | 46.857 ms | 58.629 ms | 19.801 ms | 20.763 ms |
| 10 MB 独立滚动 | 4.289 ms | 7.110 ms | 3.218 ms | 8.339 ms |

AMD 机器的测试条件为 27.8 GB 内存、Windows 11、1920 × 1080 和 100% 缩放，使用交流供电和“平衡”电源模式。不过这台电脑安装了多个杀毒软件，系统也已经使用两年多，软件环境比较杂。这些因素可能增加冷启动耗时和长尾波动，因此这里的 AMD 数据更接近真实办公环境，而不是一台刚装好系统的纯净性能测试机。

Intel 机器的测试条件为 15.8 GB 内存、Windows 11 专业版、100% 缩放、交流供电和“平衡”电源模式。它的 150 KB 与 10 MB 冷启动都更快；AMD 的 10 MB 运行中打开略快约 2 ms，基本处于同一水平。由于系统、后台负载和硬件环境不同，这些数据更适合作为整机体验参考，不适合单独推导某个硬件部件的影响。

## 极端文档也做了一轮压力测试

上面的完整表使用结构比较常规的测试文档。为了确认“包含一个巨大段落或表格”时不会重新卡住，我又单独生成了两类极端样本：

| 场景 | 文件大小 | 冷启动 P50/P95 | 首次绘制 P50/P95 |
|---|---:|---:|---:|
| 5000 行单表格 | 187 KB | 247.2 / 290.2 ms | 37.0 / 43.5 ms |
| 9.5 MB 单段落 | 9.5 MB | 261.3 / 283.4 ms | 39.1 / 45.5 ms |

连续投递 120 个滚轮事件的 150 KB 文档突发滚动测试中，平衡模式 P95 为 `4.8 ms`，最大单帧 `6.1 ms`，没有超过 16.7 ms 的帧。至少在这组真实桌面环境数据中，滚动没有出现之前担心的百毫秒级卡顿。

10 MB 冷启动的 300 ms 只是挑战目标，不属于硬性验收。Intel 的 P95 达到 `180.478 ms`，已经通过挑战目标；AMD 的 P95 为 `328.849 ms`，仍差约 29 ms。AMD 机器上 10 MB Tab 切换的 P95 也仍高于 50 ms，而 Intel 为 `20.763 ms`。这些没有统一达成的指标都保留在记录里，而不是只展示最好看的结果。

## 原生方案不等于自动变快

这次开发给我最大的提醒是：**“不用 Electron”只是减少了一层固定成本，并不能替代性能设计。**

如果仍然同步解析全文、同步布局所有块、每个 Tab 都重建整个视图，原生程序一样会卡。真正有效的改动是：

- 只让首屏等待首屏所需的数据。
- 把全文解析和网络资源加载放到后台。
- 只布局当前视口附近的块。
- 把可能无限增大的单个块继续切小。
- 用块高度索引和阅读锚点抵消延迟布局带来的滚动跳动。
- 先测量阶段耗时，再决定优化哪里。

我也刻意没有做几项看起来很“高级”的优化。位图缓存、滚动降级、按帧切块和多核分段 AST 合并都会增加内存、闪烁或正确性风险，而现有数据没有证明它们能带来稳定收益。性能优化最怕的不是方案不够复杂，而是花了复杂度却没有解决真正的瓶颈。

## 最后

这不是一个要替代 Typora、Obsidian 或 VS Code 的项目。它不编辑文件，不管理知识库，也不试图支持所有 Markdown 语法。它只解决一个很具体的问题：当一份 AI 生成的 Markdown 已经写好时，怎样在副屏上几乎无感地打开、切换和阅读。

现在我的使用方式很简单：在 VS Code 里继续修改文档，需要阅读时双击 `.md` 文件，liteMark 在已有窗口中打开一个新 Tab。再次双击同一文件，只会切回原来的 Tab。VS Code 保存修改后，liteMark 会自动检测到外部文件变化并弹出重新加载提示，确认一下就切换到更新后的内容，不需要手动关闭再打开。没有 Electron 启动画面，没有编辑器侧栏，也不需要为了看一眼正文重新排列整个 VS Code。

主体功能确实是在三个晚上里连续做出来的，但后面的测试、边界修正和发布打磨并不在这三个晚上内。真正让项目变得可用的，不只是“写完了”，而是一次次把打开时间、滚动帧、超大块和异常路径测出来，再决定哪些问题值得继续优化。
